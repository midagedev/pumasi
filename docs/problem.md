# 풀려는 문제

셀프호스트 GitHub Actions 러너를 여러 대의 머신에 깔아 쓰는 팀에서 반복해서 생기는 일이다.

## 관찰 (실측 한 사례)

| 머신 | 사양 | 러너 슬롯 | 그날 상태 |
|---|---|---|---|
| 노트북 Mac | 10코어 / 32GB | PR 진단 7 + 기타 1 + e2e 3 = 11 | load 74. e2e 잡 9개가 compose 헬스체크에서 전멸 |
| Linux 서버 | 48스레드 / 128GB | 15 | 그 시각 일부만 사용 |
| 개발자 워크스테이션 | — | e2e 4 | 주인이 작업하자 브라우저가 `ERR_NETWORK_CHANGED` 로 흰 화면, e2e 11건 실패 |

- GitHub 은 **비어 있는 슬롯이면 호스트 부하와 상관없이** 잡을 넣는다. 조절 손잡이는 슬롯 개수뿐이다.
- 잡 크기가 다르다. lint 한 번과 JVM·DB·브라우저를 띄우는 e2e 한 번이 똑같이 슬롯 1개로 계산된다.
- 그래서 운영이 "전용 풀 → 통합 풀 → 다시 분리" 를 몇 달 간격으로 오간다. 한쪽이 넘치면 라벨을 옮기는 것 말고 할 수 있는 게 없다.
- 잡이 남긴 찌꺼기(정리 단계가 타임아웃되며 남은 컨테이너·디렉터리)가 다음 잡의 자원을 갉아먹는다.
- 사람이 쓰는 머신을 러너로 빌리면 사람도 CI 도 서로 방해한다.

## 원하는 것

1. **용량에 맞춘 배치** — 잡 크기(CPU·메모리)와 호스트 여유를 보고 어느 머신에 러너를 띄울지 정한다. 자리가 없으면 GitHub 큐에서 기다리게 한다(다 받아 놓고 같이 느려지지 않는다).
2. **이기종** — Linux 서버, Linux·Windows 데스크톱, Apple Silicon Mac 을 한 컨트롤러로.
3. **사람 우선** — 데스크톱은 주인이 안 쓸 때만 일을 받고, 주인이 돌아오면 새 일을 안 받는다(HTCondor 의 owner 정책처럼).
4. **잡마다 일회용** — 러너는 잡 하나 뒤 사라진다. 찌꺼기가 남지 않는다.
5. **캐시는 따뜻하게** — 일회용이어도 의존성·빌드 캐시는 호스트에 남겨 재사용한다.

## 하지 않는 것 (지금은)

- Kubernetes 를 요구하지 않는다. 노트북·데스크톱에 클러스터를 깔게 하지 않는다.
- GitHub 이외의 CI(Gitea·GitLab)는 나중 일이다.
- 클라우드 인스턴스 자동 생성은 범위 밖이다(그건 이미 잘하는 도구가 많다).
