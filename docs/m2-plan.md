# M2 계획 — 긴 e2e 잡을 믿고 맡길 수 있게

M1 까지로 짧은 잡은 돈다([m1-results.md](m1-results.md)). M2 의 기준은 30~90분짜리 e2e 다: 러너 안에서 서버 스택을 띄우고, 브라우저를 여러 개 돌리고, 중간에 죽으면 한 시간을 버린다.

이미 된 것: controller 를 꺼도 도는 잡은 남고 다시 켜면 이어받는다. 호스트 연결이 끊겨도 잡 도는 러너는 지우지 않는다(3분 끊김 실측, 10/10 성공).

## 순서

| # | 할 일 | 왜 | 끝났다는 기준 |
|---|---|---|---|
| 1 | 실제 e2e 가 러너에 요구하는 것을 잰다 | 드라이버·클래스 크기를 추측으로 정하지 않는다 | e2e 워크플로 하나의 cpu·메모리 peak·디스크·실행 시간·docker 사용 방식 표 |
| 2 | controller 를 항상 켜진 호스트로 | 노트북이 잠들면 새 잡을 못 받는다 | `pumasi up --detach` 또는 systemd 유닛. 노트북은 `pumasi status --host <controller>` 만 |
| 3 | 러너 안에서 docker 를 쓴다 | e2e 는 compose 로 스택을 올린다. 지금 이미지는 못 한다 | 러너 안 `docker compose up` 이 되고, 그 자식 컨테이너의 자원도 러너 cgroup 에 잡힌다 |
| 4 | 호스트별 캐시 | 일회용 러너는 매번 의존성·브라우저·이미지를 새로 받는다 | 두 번째 실행의 준비 단계가 첫 실행의 1/3 이하 |
| 5 | 긴 클래스의 배치 규칙 | 90분짜리가 사람 책상을 잡으면 그동안 못 비킨다 | 클래스에 `hosts`·`servers-only`. 장부의 실행 시간으로 긴 잡은 여유 큰 호스트로 |
| 6 | 사람 우선 | 사람이 앉으면 새 러너를 안 받고 도는 잡은 끝낸다 | 데스크톱 입력 감지 → `owner-active` 동안 배치 0, 도는 잡 정지 0 |

## 3번의 선택지

| 방식 | 격리 | 자원 집계 | 비고 |
|---|---|---|---|
| 호스트 docker 소켓을 넘김 | 없음(호스트 root 와 같다) | 자식 컨테이너가 러너 cgroup 밖 | 가장 쉽지만 상한이 무너진다. 쓰지 않는다 |
| 러너 컨테이너 안 dockerd (sysbox 또는 privileged) | 중 | 러너 cgroup 안 | 1번 측정 뒤 첫 후보 |
| kata / microVM | 높음 | VM 단위로 깨끗 | /dev/kvm 필요(두 호스트 모두 있음). 기동·디스크 비용을 잰 뒤 결정 |

상한과 메트릭이 러너 단위로 유지되는 것이 조건이다. 1번 측정이 끝나면 둘째와 셋째를 같은 e2e 로 비교해 고른다.

## 하지 않는 것

- 실패한 잡의 자동 재실행. GitHub 이 재시도하지 않으므로 워크플로 쪽 책임으로 둔다.
- 잡 도중 다른 호스트로 옮기기.
