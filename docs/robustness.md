# 견고함 — 장애마다 감지·복구·알림을 정해 둔다

원칙 셋.

1. **상태는 다시 만들 수 있다.** 진실은 호스트의 컨테이너(에이전트가 본다)와 GitHub 이다. 장부는 그 둘에서 복원된다. controller 는 언제 죽어도 된다.
2. **도는 잡은 건드리지 않는다.** 복구 동작은 잡 없는 러너와 새 배치에만 손댄다. 예외는 사용자가 명시한 것(`down --force`, 클래스의 `maxDuration`)뿐이다.
3. **조용히 실패하지 않는다.** 스스로 고친 것도, 못 고친 것도 사건(incident)으로 남기고 알린다.

## 사건 (incident)

장부의 `incidents(key, kind, subject, opened_at, resolved_at, detail, action)`. `key` 가 같으면 같은 사건이다(예: `host-unreachable/server1`). 열릴 때 한 번, 닫힐 때 한 번 알린다. 열린 채 오래가면 30분마다 다시 알린다. `pumasi status` 맨 위 `PROBLEMS` 절에 열린 사건이 나온다. 없으면 절 자체가 없다.

## 장애 표

| 장애 | 감지 | 자동 복구 | 알림 |
|---|---|---|---|
| controller 프로세스 죽음 | 서비스 관리자(systemd·launchd) | 재시작 → 잠금 → 에이전트·러너 이어받기, 놓친 메시지는 에이전트 스냅샷과 GitHub 잡 상태로 메움 | 올라올 때 "N분 꺼져 있었음, 러너 N개 이어받음, 그 사이 끝난 잡 N" |
| controller 가 오래 꺼져 있음 | 에이전트: controller 의 마지막 호출이 5분 넘음 | 없음(에이전트는 러너를 그대로 둔다) | 호스트에 `notify` 가 있으면 에이전트가 직접 알림 |
| 에이전트 죽음 | controller: 20초 무응답 | ssh 로 다시 올림(컨테이너 안 건드림). 에이전트는 러너 수치를 디스크에 두어 재시작 뒤에도 최종 값이 남는다 | 3번 연속 실패하면 사건 |
| 호스트 연결 끊김 | 터널·스냅샷 실패 | 새 배치 중단, 러너는 용량에 그대로 계산, 돌아오면 스냅샷으로 맞춤 | 2분 넘으면 사건, 돌아오면 해제 |
| 호스트 재부팅 | 에이전트 boot id 가 바뀜, 러너 컨테이너가 사라짐 | 그 러너를 lost 로 닫고 등록 삭제. 돌던 잡은 **인프라 실패**로 기록 → 아래 재실행 | 사건 + 잃은 잡 목록 |
| 러너가 기동 못 함 | `provisionTimeout`, 컨테이너 조기 종료 | 지우고 다른 호스트에 다시 배치 | 같은 호스트에서 연속 3번이면 그 호스트 격리(아래) |
| 호스트가 계속 실패 | 연속 기동 실패 3번 | **격리**: 새 배치 중단, 5분마다 시험 러너 없이 점검(docker·디스크·이미지), 통과하면 복귀 | 격리·복귀 각각 |
| 잡 도중 러너가 죽음 | 컨테이너 exit ≠ 0 인데 잡 완료 메시지 없음, 또는 외부 kill | 등록 삭제(GitHub 이 놓을 때까지 재시도). **인프라 실패**로 기록 → 재실행 | 사건 + 잡·호스트·exit code |
| 러너가 메모리 상한에 걸림 | cgroup `memory.events` 의 `oom_kill` 증가 | 없음(코드·클래스 문제). 재실행하지 않는다 | "잡 X 가 linux-l 3G 상한에 걸림, peak 3.0G" |
| 잡이 너무 오래 기다림 | 수요의 처음 본 시각 + `waitAlert`(기본 10분) | 재평가는 계속 | 사건 + 사유("no host with 2cpu/3G free …"), 시작되면 해제 |
| 잡이 너무 오래 돎 | 클래스 `maxDuration`(기본 없음) | 설정했을 때만 러너 정지 | 넘는 순간 사건 |
| 호스트 디스크 부족 | 에이전트가 docker 루트의 여유를 보고 | 임계(기본 10%) 아래면 새 배치 중단, 끝난 pumasi 컨테이너·안 쓰는 러너 이미지 정리 | 사건, 회복되면 해제 |
| GitHub API 실패·토큰 만료·세션 충돌 | 호출 오류 | 지수 백오프로 재시도. 401·403 은 재시도 안 하고 멈춤 | 2분 넘으면 사건. 401·403 은 즉시 |
| 장부가 깨짐 | 열기·무결성 검사 실패 | 옆으로 치우고(`pumasi.db.broken-<시각>`) 빈 장부에서 시작, 에이전트 스냅샷과 GitHub 으로 러너·수요 복원 | 사건(이력은 잃음) |
| 주인 없는 것 | 주기 점검: 장부에 없는 pumasi 컨테이너, 러너 없는 등록 | 잡 없는 것만 지움 | 지운 수를 로그에, 반복되면 사건 |
| controller 두 개 | 상태 디렉터리 잠금 | 두 번째가 바로 끝남 | 오류 한 줄 |

## 인프라 실패의 재실행

잡이 실패했을 때 원인이 우리 쪽이면(호스트 재부팅, 러너 외부 종료, 호스트 유실 중 컨테이너 소실) GitHub 의 `rerun-failed-jobs` 를 부른다. 조건:

- 설정 `rerun: 1`(기본 0 = 알리기만 한다). 값은 실행(run)당 최대 횟수.
- 코드 실패·메모리 상한·`maxDuration` 초과는 인프라 실패가 아니다. 재실행하지 않는다.
- 재실행도 사건의 `action` 에 남기고 알린다("large (2) 를 재실행함: server1 재부팅").

## 알림

```yaml
notify:
  webhook: https://…            # JSON POST. Slack·Teams 수신 웹훅이면 그 형식으로 보낸다
  command: my-notify --stdin    # 또는 명령. 사건 JSON 을 stdin 으로 받는다
  level: problem                # problem(기본) | recovered | all
```

- 한 사건은 한 줄이다: `[pumasi] server1 unreachable for 2m — 3 jobs still running there, no new runners placed`. 해제는 `resolved after 4m`.
- 같은 `key` 는 열림·30분 재알림·해제만 보낸다. 5분 안에 열렸다 닫히는 것이 3번 넘으면 "flapping" 한 번으로 묶는다.
- 알림 전송 실패는 장부에 남기고 다음 평가 때 다시 보낸다. 알림이 막혀도 배치는 멈추지 않는다.
- 웹훅 주소는 controller 에만 둔다. 호스트의 에이전트 알림은 그 호스트에 따로 적은 `command` 로만 한다.

## 확인 방법

장애 표의 행마다 실제 호스트에서 일으켜 보는 스크립트(`make chaos`)를 둔다: 에이전트 kill, controller kill -9, 터널 끊기, 러너 kill(기동 중·잡 도중), 메모리 상한 넘기기, 디스크 임계 낮추기, 장부 파일 훼손, 잘못된 토큰. 행마다 기대 결과는 "잡 결과 · 열린 사건 · 온 알림 · 닫힌 사건". 통과한 행만 README 에 "복구됨"으로 적는다.
